|-----------|---------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1         | Отсутствие observability                                                                                            | Без видимости невозможно расследовать потерю заказов, измерить задержки, доказать, где именно ломается интеграция. Слепое управление системой.                                                                                 | **И1. Observability (мониторинг + трейсинг + логи)** <br><ul><li>**Трейсинг:** интегрировать OpenTelemetry SDK во все сервисы (Java, C#, фронтенд). Настроить экспорт трейсов в Jaeger. Добавить контекстные спаны для каждого бизнес-шага (получение заказа, расчёт стоимости, отправка в очередь, обновление статуса).</li> <li>**Метрики:** подключить Prometheus exporters (через micrometer в Java, OpenTelemetry метрики в C#). Собирать: время ответа эндпоинтов/rps/ошибки, глубину очередей RabbitMQ, количество заказов в статусах, ошибки интеграций и пр. Визуализировать в Grafana (дашборды для операторов, поддержки, бизнеса).</li> <li>**Логи:** централизованный сбор логов всех сервисов в ELK (+ Grafana). Добавить trace-id в каждое сообщение лога, чтобы связывать логи с трейсами. </li></ul> <br> Ожидаемый результат: возможность за 2 минуты найти, на каком этапе завис любой конкретный заказ, измерить время расчёта, увидеть переполнение очереди. |
| 2         | Долгая обработка расчёта стоимости (2–30 мин) без надёжной обратной связи с клиентом и без гарантий доставки задачи | Пользователь (или внешний партнёр) не видит прогресса, не получает уведомления о завершении, а в случае ошибки расчёт теряется. Это приводит к тому, что заказы зависают в статусе `SUBMITTED` или `PRICE_CALCULATED` надолго. | **И2. Внедрение надёжного механизма оповещения о завершении длительных операций.**  <br><ul><li>Добавить явные уведомления: webhook для внешних API, polling или WebSocket для онлайн-магазина.</li>  <li>Результат расчёта сохраняется в хранилище состояний задач (например, Redis с TTL 24 часа), чтобы клиент мог получить его по taskId. </li><li>Клиент получает `taskId` сразу (202 Accepted) и опрашивает статус `GET /task/{taskId}`.   </li></ul>                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 3         | Ненадёжная интеграция через RabbitMQ (потери сообщений, отсутствие ретраев, dead-letter)                            | При росте заказов очередь переполняется, заказы теряются. Клиенты жалуются, что "заказ не получен". CRM не узнаёт о новых заказах.                                                                                             | **И3. Повышение надёжности RabbitMQ** <br><ul><li>**Publisher confirms:** настроить подтверждения от брокера на стороне отправителя (онлайн-магазин, MES). При неудаче – повторная отправка с экспоненциальной задержкой (до 3 попыток).</li> <li>**Dead‑letter exchanges (DLX):** для каждой рабочей очереди создать DLX, куда будут попадать сообщения, которые не удалось обработать после N ретраев. Из DLX – отдельный механизм алертов и ручного вмешательства.</li><li>**Мониторинг очередей:** собирать метрику длины очереди в Prometheus, настроить алерт при превышении 1000 сообщений.</li></ul> <br> Ожидаемый результат: нулевая потеря сообщений при нормальной работе, автоматическое восстановление после кратковременных сбоев, видимость проблемных сообщений.                                                                                                                                                                                                 |
