# Задание 2. Мониторинг

## 1. Мотивация

### Почему нужен мониторинг и что он даст компании

Бизнес Александрита теряет деньги из‑за невыполненных заказов, ухода клиентов и разрыва контрактов с партнерами. При этом у команды нет объективных данных о том, где именно происходит сбой: в MES, в очереди RabbitMQ, в CRM или на уровне инфраструктуры.

### Внедрение мониторинга позволит:

- **Обнаруживать проблемы до того, как на них пожалуется бизнес.** \
Например, рост глубины очереди RabbitMQ или увеличение времени расчета стоимости в MES автоматически вызовут алерт, и дежурный инженер сможет вмешаться за 10–20 минут до массовых жалоб.

- **Расследовать инциденты по факту.** \
Потерялся заказ? По метрикам и трейсам мы быстро найдем, на каком этапе он завис: не ушел в очередь, не обработался MES или не обновился в CRM.

- **Планировать масштабирование и ресурсы** \
Метрики RPS, CPU, памяти, размера БД покажут, когда пора добавлять инстансы или увеличивать реплики. Это удержит рост расходов под контролем.

- **Измерять эффективность изменений.** \
После оптимизации дашборда MES или введения асинхронного расчета мы увидим реальное снижение latency.

- **Повышать доверие бизнеса и партнеров.** \
С отчетностью по SLA (99.9% доступности API) и прозрачными метриками легче заключать контракты.


## 2. Выбор подхода к мониторингу

Мы используем комбинацию подходов USE и RED, а также "Четыре золотых сигнала" Google.

| Компонент системы                               | Подход                                                   | Обоснование                                                                                                                  |
|-------------------------------------------------|----------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------|
| Инфраструктура (CPU, память, диск, сеть, БД)    | USE (Utilization, Saturation, Errors)                    | Для физических ресурсов важно знать их загрузку, насыщение и ошибки ввода‑вывода.                                            |
| Прикладные сервисы (Shop API, CRM API, MES API) | RED (Rate, Errors, Duration)                             | Для каждого эндпоинта нужно измерять количество запросов, долю ошибок и время ответа – это напрямую влияет на пользователей. |
| Интеграционные слои (RabbitMQ, S3, внешние API) | Золотые сигналы (Latency, Traffic, Errors, Saturation)   | Очередь – классический пример насыщения. S3 – трафик и latency.                                                              |

## 3. Метрики и ярлыки (labels)

### 3.1. Инфраструктура и базовые компоненты

| Метрика                                        | Зачем нужна                                                                                                   | labels                                                                        |
|------------------------------------------------|---------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| CPU % для Shop/CRM/MES API                     | Отслеживать перегрузку приложений, планировать масштабирование.                                               | `service` (`shop`/`crm`/`mes`), `instance_id`, `env` (`dev`/`release`/`prod`) |
| Memory Utilisation для Shop/CRM/MES API        | Предотвращать утечки памяти, падения по OOM.                                                                  | те же                                                                         |
| Memory Utilisation для БД (shop db, MES db)    | Базы данных – частое узкое место. Высокая память может означать неэффективные запросы или недостаток буферов. | `db_instance`, `role` (`master`/`replica`)                                    |
| Number of connections для БД (shop db, MES db) | Слишком много подключений исчерпывают ресурсы БД, приводят к отказам.                                         | `db_instance`, `app_name` (какой сервис подключился)                          |
| Size of shop db instance / MES db instance     | Мониторинг роста данных для планирования дискового пространства и архивации.                                  | `db_instance`, `table_schema`                                                 |
| Size of S3 storage                             | Контроль затрат на хранение 3D‑файлов, прогнозирование бюджета.                                               | `bucket`, `storage_class`                                                     |

### 3.2. Прикладные API (метрики RED)

| Метрика                                              | Зачем нужна                                                                      | labels                                                                                 |
|------------------------------------------------------|----------------------------------------------------------------------------------|----------------------------------------------------------------------------------------|
| Number of requests (RPS) для Shop/CRM/MES API        | Измерять трафик, обнаруживать аномальные скачки (DDOS, ошибка в клиенте).        | `service`, `endpoint` (например, `/buy`, `/calculate`, `/orders`), `method` (GET/POST) |
| Response time (latency) для Shop/CRM/MES API         | Основной показатель качества обслуживания. Долгое время ответа -> уход клиентов. | `service`, `endpoint`, `quantile` (p50, p95, p99)                                      |
| Number of HTTP 200/4xx/5xx для Shop/CRM/MES API      | Ошибки 500 напрямую влияют на бизнес.                                            | `service`, `endpoint`, `status_code`                                                   |
| Number of simultaneous sessions для Shop/CRM/MES API | Помогает оценить реальную нагрузку на память и число активных пользователей.     | `service`                                                                              |
| Kb transferred (received/sent)                       | Анализ трафика, выявление тяжелых запросов.                                      | `service`, `endpoint`, `direction` (in/out)                                            |

### 3.3. RabbitMQ – золотые сигналы
| Метрика                                                | Зачем нужна                                                                                                           | labels                                                                |
|--------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| Number of messages published / acknowledged / rejected | Мониторинг потока, обнаружение застрявших сообщений.                                                                  | `queue_name`                                                          |
| Read lag                                               | Основная метрика насыщения очереди. При превышении порога (например, > 1000) – алерт и авто-масштабирование воркеров. | `queue_name`                                                          |
| Number of dead-letter-exchange letters in RabbitMQ     | Прямой индикатор потерянных заказов. Если DLX растет – сообщения не обрабатываются после всех ретраев.                | `queue_name`, `exchange`, `reason` (например, `max_retries_exceeded`) |
| Number of messages in flight in RabbitMQ               | Текущая глубина очереди.                                                                                              | `queue_name`                                                          |
| Message processing time (от публикации до ack)         | Измеряет эффективность воркеров, задержки обработки.                                                                  | `queue_name`, `consumer_tag`                                          |

### 3.4. Дополнительные бизнес-метрики

| Метрика                                                                           | Зачем нужна                                                                                                                 | labels                                                                     |
|-----------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| Number of orders stuck in status (например, `SUBMITTED` > 1 час)                  | Прямое измерение проблемы "потерянных заказов".                                                                             | `status`, `service_responsible` (Shop/MES/CRM)                             |
| Calculation task age (время с момента создания задачи расчета до завершения)      | Контроль SLA расчета стоимости (обещано 2‑3 минуты, реально – 30 минут).                                                    | `model_complexity` (simple/medium/complex)                                 |
| Total orders created per hour                                                     | Видеть общий поток заказов, сезонность, эффект маркетинговых акций. Резкий спад -> возможно, сломан онлайн‑магазин или API. | `source` (shop / external_api), `product_category` (кольца, серьги и т.д.) |
| Average order completion time (от `INITIATED` до `SHIPPED`/`CLOSED`)              | Показатель эффективности производства. Если растет -> где‑то узкое место (расчет, очередь, операторы).                      | `product_category` (кольца, серьги и т.д.)                                 |
| Number of price calculation requests per hour                                     | Нагрузка на MES и очередь. Можно сравнить с числом созданных заказов – можно оценивать конверсию из расчетов в заказ.       | `model_complexity` (simple/medium/complex)                                 |
| Calculation success rate (`successful_calculations / total_calculation_requests`) | Доля расчетов, завершившихся без ошибок. Падение ниже 95% -> проблемы в MES или очереди.                                    | `model_complexity` (simple/medium/complex)                                 |
| Number of orders by status (splitted by hour)                                     | Мониторинг распределения: много заказов в `MANUFACTURING_APPROVED` – возможно, CRM не отправляет в производство.            | `status`                                                                   |
| API partner order inflow per partner                                              | Контроль, какие внешние партнеры дают больше всего заказов, а какие перестали обращаться (возможно, у них ошибки).          | `partner_id`, `api_version`                                                |
| SLA compliance rate (доля заказов, выполненных за 3 недели)                       | Ключевая бизнес-метрика – если падает, компания теряет репутацию и платит штрафы.                                           | `customer_type` (B2C / B2B)                                                |

Как использовать:
- Эти метрики собираются из логов и БД (через экспортер метрик, например, из PostgreSQL с помощью `pg_stat_statements` или отдельных запросов каждую минуту).
- Дашборд в Grafana для руководителей (среднее время выполнения заказа, заказы в час).
- Алерты на критические значения: ">10 заказов в статусе `SUBMITTED` дольше 2 часов" -> инцидент.

## 5. Дополнительное задание: показатели насыщенности и действия

| Компонент         | Метрика насыщенности                           | Пороговое значение                                                  | Действие при превышении                                                                                                                                                                                                                                                             |
|-------------------|------------------------------------------------|---------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Shop/CRM/MES API  | CPU utilization                                | > 80% в течение 10 минут                                            | 1. Алерт. Отправить предупреждение в мессенджер. <br> 2. Автоматически добавить новый инстанс (auto‑scaling group).                                                                                                                                                                 |
| Shop/CRM/MES API  | Memory utilization                             | > 90%                                                               | 1. Алерт. Отправить предупреждение в мессенджер. <br> 2. Дамп heap (Java) / core dump (C#) для анализа. <br> 3. Принудительный рестарт контейнера.                                                                                                                                  |
| PostgreSQL БД     | Количество подключений                         | > 80% от `max_connections`                                          | 1. Алерт. Отправить предупреждение в мессенджер. <br> 2. Увеличить лимит подключений через конфигурацию managed service. <br> 3. Анализ приложений, не закрывающих соединения.                                                                                                      |
| RabbitMQ          | Number of messages in flight (глубина очереди) | > 1000 сообщений в очереди `calc_tasks`                             | 1. Срочный алерт (critical). Отправить предупреждение в мессенджер. <br> 2. Автоматически увеличить количество воркеров (k8s HPA или запуск дополнительных EC2). <br> 3. Если не снижается за 15 минут – эскалация в чат техподдержки.                                              |
| RabbitMQ          | Dead‑letter count                              | > 0 (мониторинг появления)                                          | 1. Алерт. Отправить предупреждение в мессенджер – проверить очередь DLX. <br> 2. Завести задачу в Jira на анализ причины. <br> 3. Для критичных заказов – скрипт повторного помещения в исходную очередь после исправления.                                                         |
| API latency (p95) | Время ответа для /calculate (MES)              | > 2 секунд (это должен быть только запрос статуса, а не сам расчет) | 1. Алерт. Отправить предупреждение в мессенджер. <br> 2. Проверить доступность RabbitMQ (очередь calc_tasks) – возможно, брокер перегружен. <br> 3. Проверить latency Redis (хранилище `taskId`). <br> 4. Увеличить число воркеров для обработки очереди (не для самого эндпоинта). |
| S3 storage        | Размер хранилища                               | > 80% от выделенной квоты                                           | 1. Алерт. Отправить предупреждение в мессенджер. <br> 2. Автоматически запустить policy lifecycle (перемещение старых файлов в glacier или удаление). <br> 3. Увеличение квоты при необходимости.                                                                                   |
