# Задание 1. Планирование: анализ, идентификация проблем и поиск решений

| Приоритет | Проблема                                                                                                            | Обоснование                                                                                                                                                                                                                    | Инициатива для решения проблемы                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
|-----------|---------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1         | Отсутствие observability                                                                                            | Без видимости невозможно расследовать потерю заказов, измерить задержки, доказать, где именно ломается интеграция. Слепое управление системой.                                                                                 | **И1. Observability (мониторинг + трейсинг + логи)** <br><ul><li>**Трейсинг:** интегрировать OpenTelemetry SDK во все сервисы (Java, C#, фронтенд). Настроить экспорт трейсов в Jaeger. Добавить контекстные спаны для каждого бизнес-шага (получение заказа, расчет стоимости, отправка в очередь, обновление статуса).</li> <li>**Метрики:** подключить Prometheus exporters (через micrometer в Java, OpenTelemetry метрики в C#). Собирать: время ответа эндпоинтов/rps/ошибки, глубину очередей RabbitMQ, количество заказов в статусах, ошибки интеграций и пр. Визуализировать в Grafana (дашборды для операторов, поддержки, бизнеса).</li> <li>**Логи:** централизованный сбор логов всех сервисов в ELK (+ Grafana). Добавить trace-id в каждое сообщение лога, чтобы связывать логи с трейсами. </li></ul> <br> Ожидаемый результат: возможность за 2 минуты найти, на каком этапе завис любой конкретный заказ, измерить время расчета, увидеть переполнение очереди. |
| 2         | Долгая обработка расчета стоимости (2–30 мин) без надежной обратной связи с клиентом и без гарантий доставки задачи | Пользователь (или внешний партнер) не видит прогресса, не получает уведомления о завершении, а в случае ошибки расчет теряется. Это приводит к тому, что заказы зависают в статусе `SUBMITTED` или `PRICE_CALCULATED` надолго. | **И2. Внедрение надежного механизма оповещения о завершении длительных операций рачета.**  <br><ul><li>Добавить явные уведомления: webhook для внешних API, polling или WebSocket для онлайн-магазина.</li>  <li>Результат расчета сохраняется в хранилище состояний задач (например, Redis с TTL 24 часа), чтобы клиент мог получить его по `task_id`. </li><li>Клиент получает `task_id` сразу (202 Accepted) и опрашивает статус `GET /task/{task_id}`.   </li></ul>  <br> Ожидаемый результат: клиент получает ответ за <1 секунды, а гарантированная очередь и хранилище состояний исключают потерю запросов и позволяют масштабировать обработку.                                                                                                                                                                                                                                                                                                                           |
| 3         | Ненадежная интеграция через RabbitMQ (потери сообщений, отсутствие ретраев, dead-letter)                            | При росте заказов очередь переполняется, заказы теряются. Клиенты жалуются, что "заказ не получен". CRM не узнает о новых заказах.                                                                                             | **И3. Повышение надежности RabbitMQ** <br><ul><li>**Publisher confirms:** настроить подтверждения от брокера на стороне отправителя (онлайн-магазин, MES). При неудаче – повторная отправка с экспоненциальной задержкой (до 3 попыток).</li> <li>**Dead‑letter exchanges (DLX):** для каждой рабочей очереди создать DLX, куда будут попадать сообщения, которые не удалось обработать после N ретраев. Из DLX – отдельный механизм алертов и ручного вмешательства.</li><li>**Мониторинг очередей:** собирать метрику длины очереди в Prometheus, настроить алерт при превышении 1000 сообщений.</li></ul> <br> Ожидаемый результат: нулевая потеря сообщений при нормальной работе, автоматическое восстановление после кратковременных сбоев, видимость проблемных сообщений.                                                                                                                                                                                                 |
| 4         | Отсутствие горизонтального масштабирования                                                                          | Нагрузка растет (внешние API +100 заказов/мес). Один сервер MES, CRM и БД становится узким местом, появляются задержки и отказы.                                                                                               | **И4.Горизонтальное масштабирование**<br> <ul><li>**Приложения:** – Добавить балансировщик (Application Load Balancer в Yandex Cloud / AWS) перед каждым сервисом. – Настроить auto-scaling группы EC2 (или перейти на управляемый контейнерный сервис, но для быстрого эффекта – EC2). – Минимум 2 инстанса каждого приложения (SHOP API, CRM API, MES API) в разных зонах доступности.</li><li>**Базы данных:** – Для PostgreSQL (Shop DB, MES db) добавить реплику для чтения. Настроить в приложениях разделение: запись идет на мастер, чтение (дашборды, отчеты) – на реплику. – Подключить мониторинг репликации.</li><li>**Состояние:** убедиться, что приложения не хранят состояние локально (сессии вынести в Redis, загрузку файлов – в S3).</li></ul><br>Ожидаемый результат: система выдерживает двукратный рост нагрузки без деградации, отказ одного инстанса не приводит к остановке.                                                                            |
| 5         | Единая точка отказа БД (один инстанс на чтение/запись)                                                              | При сбое БД вся система останавливается. При росте нагрузки производительность падает из-за смешанной нагрузки.                                                                                                                | (Входит в И4 как подпункт) – см. выше про репликацию и, возможно, настройку автоматического failover (Managed service для PostgreSQL в Yandex Cloud позволяет создать кластер с несколькими мастерами).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 6         | Низкая производительность дашборда MES                                                                              | Операторы теряют время, страдает их вознаграждение (кто первый взял заказ). Фильтр и пагинация не решили проблему.                                                                                                             | **И5. Оптимизация дашборда MES**<br><ul><li>**Индексы БД:** добавить составные индексы по полям `status` + `created_at` в таблице заказов MES.</li> <li>**Кэширование часто повторяющихся запросов:** использовать Redis для хранения результата агрегированной статистики (количество заказов по статусам) на 30 секунд.</li> <li>**Пагинация на основе курсора:** заменить классическую `OFFSET/LIMIT` на курсор (например, по `сreated_at` и `id`). Это ускорит переход между страницами.</li>  <li>**Read‑модель (CQRS):** создать отдельную таблицу (или материализованное представление) `orders_read`, которая обновляется асинхронно через события. На нее повесить все необходимые индексы. </li> <li>**Виртуализация списка на фронтенде (React):** загружать только 20 записей и подгружать по мере скролла.</li> </ul> <br> Ожидаемый результат: время загрузки дашборда сокращается с нескольких секунд до <300 мс.                                                  |
| 7         | Отсутствие кэширования                                                                                              | Повторные запросы грузят БД и сеть, увеличивая задержки дашборда и время загрузки 3D-моделей.                                                                                                                                  | **И6. Кэширование** <br> <ul><li>**Redis:** – Справочники (типы изделий, статусы) – кэш на 1 час. – Результаты расчета стоимости для одной сессии – на 30 минут (чтобы не пересчитывать при повторном обращении). – Текущие сессии пользователей (замена локального state).</li> <li>**CDN:** загружаемые пользователями 3D-файлы (.stl, .obj) и сгенерированные превью складывать в S3-совместимое хранилище, раздать через Yandex CDN.</li> <li>**HTTP-кэширование** для статики фронтенда (JS, CSS) с долгим TTL.</li> </ul><br> Ожидаемый результат: снижение нагрузки на БД на 50-70%, ускорение загрузки дашборда и 3D-моделей.                                                                                                                                                                                                                                                                                                                                             |
| 8         | API для внешних продавцов без защиты и мониторинга                                                                  | Нет rate limiting, retry, circuit breaker. Один партнер может перегрузить API. Жалобы на неполученные заказы.                                                                                                                  | **И7. API gateway + управление трафиком** <br> <ul><li>**Выбрать gateway:** Kong (open source) или Spring Cloud Gateway. Разместить перед всеми внешними API.</li> <li>**Rate limiting:** для каждого партнера лимит – например, 100 запросов в минуту на создание заказа.</li> <li>**Retry и circuit breaker:** для вызовов MES при расчете – повторять 2 раза с задержкой, если MES отвечает 5xx. При большом количестве ошибок – открыть circuit breaker на 30 секунд.</li> <li>**Логирование всех запросов** (какой партнер, эндпоинт, статус ответа, длительность) в центральный лог.</li> <li>**Мониторинг:** дашборд по использованию API (топ партнеров, ошибки, latency).</li></ul> <br> Ожидаемый результат: защита от перегрузок, прозрачность использования API, возможность строить SLA с партнерами.                                                                                                                                                                |
| 9         | Ручное E2E тестирование как единственный QA                                                                         | Релизы задерживаются на недели из-за найденных вручную high-багов. Бизнес теряет контракты.                                                                                                                                    | **И8. Автоматизация QA** <br> <ul><li>**E2E-тесты критических сценариев** (создание заказа онлайн, расчет стоимости, переход статусов до `SHIPPED`) – использовать Cypress или Playwright. Прогонять на dev-окружении после каждого мерджа.</li> <li>**API-тесты для всех эндпоинтов** (Spring Boot – @WebMvcTest, для C# – интеграционные тесты).</li> <li>**Нагрузочное тестирование** с помощью Locust или JMeter (сценарий: 100 параллельных созданий заказов). Запускать перед релизом в release-окружение.</li> <li>Включить обязательное прохождение тестов в CI/CD (GitHub Actions / GitLab CI) для веток release и main.</li></ul> <br> Ожидаемый результат: релизы перестают задерживаться из-за регрессий; high-баги ловятся автотестами в течение часа после коммита.                                                                                                                                                                                                 |
| 10        | Статусы заказов распределены по трем системам                                                                       | Нет единой картины жизненного цикла заказа, сложно отлаживать интеграцию и строить отчеты.                                                                                                                                     | **И9. Единый сервис статусов (event sourcing)** <br> <ul><li>Все изменения статуса публиковать в общий event stream (Kafka или RabbitMQ с topic order_events).</li><li>Сервис‑агрегатор (микросервис на Java или Go) подписывается на события, сохраняет текущее состояние заказа в своей БД (PostgreSQL) и историю изменений.</li><li>Предоставить API для получения состояния любого заказа и истории по `trace_id`.</li><li>Миграция: постепенно переводить CRM, MES, онлайн‑магазин на чтение статусов из нового сервиса, а не из своих локальных таблиц.</li></ul> <br> Ожидаемый результат: единый источник правды по заказам, упрощение отладки и построения бизнес-отчетов.                                                                                                                                                                                                                                                                                               |


**Порядок выполнения (roadmap) на полгода:**

- **И1 Observability** – быстрый старт, дает понимание системы.
- **И2, И3 Результат расчета стоимости + надежность очередей** – решает главные бизнес-потери заказов.
- **И4 Масштабирование** – позволяет держать рост нагрузки.

Далее – И5 оптимизация дашборда, И6 кэширование, И7 API gateway, И8 автоматизация тестов, и в конце – И9 рефакторинг статусов.
